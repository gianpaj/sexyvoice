# Should SexyVoice own the Inworld call worker?

**Assessment date** 2026-11-23

**Source baselines** SexyVoice `b0dcb1c3` and SexyCall `eb0cc63`

## Recommendation

**Continue the port of the Inworld TTS cascade into `apps/voice-agent` and make the production switch conditional.** The strongest case for TypeScript is the shared text-and-voice product. The web app and worker can use the same validated character, conversation, turn, and usage contracts. A change to chat-to-call continuity can ship with its tests in one PR. Hosting the worker remains a separate operation from hosting Next.js, and the Python service still has work to do after an Inworld-only cutover. A reduction in hosting cost or operational load needs evidence.

1. **Port Inworld only to the existing JS worker.** First run it as a deployed internal service with isolated data and shadow accounting. Keep Python available to route new calls back during the pilot. This is my pick because the local spike already proves the user interaction and shares the reply generator with text chat.
2. **Ship the product on the Python cascade first.** Add shared thread admission and text turns to the existing Python agent. This is the fallback if JS loses on voice quality, deploy behavior, billing correctness, or maintenance. It ships on the proven Python lifecycle but requires cross-repo contracts and integration tests.
3. **Move Python source into the web monorepo.** This can improve code discoverability or review coordination if those are the only problems. It still leaves two languages, package managers, and deployable processes, and adds repo and CI migration work. It does little for the shared reply path.

The local spike supports a deployed internal trial. Keep paid calls on Python until the evidence below is in. The original spike plan owns the broader product and browser scenarios. [LiveKit spike plan](2026-11-16-livekit-voice-chat.md)

## What we have and what we would inherit

Text chat uses Next.js and can run without a room. The current JS worker rejects non-loopback Supabase URLs, the token route requires local development, and the call is capped at five minutes. The checked-in worker has no container or hosting workflow. Removing those guards by itself would expose a worker designed for local tests. ## Deployment

Keep three boundaries. Next.js authenticates and issues a short-lived, server-authorized dispatch. LiveKit carries media and dispatches a named worker. Supabase holds conversation and financial state. Package and release the Node worker independently from Next.js. A long call depends on the worker and LiveKit staying connected, so Vercel request duration is outside the voice path. [LiveKit worker networking](https://docs.livekit.io/deploy/custom/deployments/)

| Host                               | What it buys                                                                                                                                                                    | What to verify                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LiveKit Cloud Agent deployment** | Managed placement, scaling, readiness-based rollout, and up to one hour for an old production worker to finish sessions. My first choice for proving long-call deploy behavior. | Use a separate test project and its production-class deployment lifecycle for the drain and rollback rehearsal. Named non-production deployments share agent secrets, cold-start, and disconnect active sessions on redeploy. Confirm plan limits, region, available replicas, rollback behavior and the effective SDK drain deadline. A configured one-hour maximum leaves little margin for setup and finalization at the call limit. [Deployment lifecycle](https://docs.livekit.io/deploy/agents/managing-deployments/), [named deployments](https://docs.livekit.io/deploy/agents/deployments/), [server options](https://docs.livekit.io/agents/server/options/) |
| **Separate Fly app**               | Reuses the existing host, CI patterns and incident knowledge. A simple always-running worker with a private health check is enough for the benchmark.                           | The current Python Fly configuration has a 300-second stop window. Blue-green rollout alone cannot guarantee a 30–60 minute conversation survives that stop. To meet that requirement on Fly, prove a release procedure that stops new dispatches to retiring workers, waits for active jobs to finish, and then stops them. Compare that maintenance with managed hosting. [SexyCall Fly config](https://github.com/gianpaj/sexycall/blob/eb0cc63/fly.toml), [Fly worker lifecycle](https://fly.io/learn/background-workers/)                                                                                                                                         |

Pick one deployment target for the proof. Use Fly if the existing host is a hard constraint and the team accepts the drain work. Otherwise start with LiveKit Cloud, subject to its project plan and cost. Use one production-like image throughout tests and release.

- **Build.** Use Node 24, the locked pnpm workspace and a glibc-based Linux runtime image with CA certificates. The build context needs the worker package, `packages/voice-chat`, workspace files and the xAI patch. Include compatible RTC and Silero native assets, prefetch required assets during build, run as an unprivileged user, and boot with `start`. Smoke-test the exact image for CLI startup, VAD prewarm and real room registration. The monorepo can build a worker-only image without bundling the Next app. [Node starter image](https://github.com/livekit-examples/agent-starter-node/blob/main/Dockerfile), [LiveKit build requirements](https://docs.livekit.io/deploy/agents/builds/)
- **Access.** Make internal and customer routes explicit, default off, and use server-owned cohort and provider selection. Keep a distinct JS dispatch name and validate version, expiry, room, user, character and voice on admission. Select scoped environment credentials for LiveKit, Supabase, xAI, Inworld and embeddings. Use physically separate staging data and provider credentials where available. Verify consented clone access in the selected Inworld workspace. Deny foreign, deleted or revoked resources before provider work.
- **Operate.** Check that the worker can receive jobs as well as pass an HTTP check. Measure active jobs, acceptance rates, prewarm time, resource use, provider limits and region latency. Budget concurrent jobs and calls per user. Deploy only after image and contract checks. Serialize deploys, mark logs with the Git SHA, and keep the previous known-good image available. Avoid cancelling an in-progress rollout. [Existing Fly workflow](https://github.com/gianpaj/sexycall/blob/eb0cc63/.github/workflows/fly.yml)
- **Drain and recover.** Retire capacity from new dispatches before stopping it. Test deployment and rollback with a 30-minute call in progress and test the configured maximum-duration path. On forced loss, expire or reconcile the exact lease and settle based on durable evidence. Let the user explicitly redial from the last committed turns. A media reconnect to the same job and a fresh job after worker loss have different guarantees.

## Production contracts that need evidence

### Billing, call limits, and storage

Port the behavior into the existing DB and JS worker. Keep one authoritative wallet writer per call. Preserve existing preflight checks and the 30-second heartbeat. Python's reference behavior starts the clock just before the providers start, makes the call eligible only after the agent first speaks, waives a call under ten whole seconds, and charges 500 credits per started 30-second bucket. At the reference boundaries, 9 whole seconds cost zero, 10 and 30 cost 500, and 31 cost 1,000 if the character spoke. A silent call can still incur provider cost. Preserve low-balance warnings, depletion handling, billing failure handling and the 60-minute Python ceiling unless the pilot advertises a smaller cap. Typed turns during a call belong to that call's charge. Standalone chat settlement is a separate contract. [Python bucket rules](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/billing.py), [metering state](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/billing_session.py), [heartbeat and limits](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/call_tracker.py)

- **Admission.** JS currently uses a six-minute lease shared with text chat. Python checks `call_sessions`. Each can accept while the other considers the user idle. Before opening up either entry point to the same cohort, ensure both runtimes and text share one admission decision, or prove exclusive per-account routing including old tokens and alternate entry points. For longer calls, use a renewable lease fenced to the admitted room/call and test stale-worker writes after expiry. Race two tabs, two characters, chat vs. call, and Python vs. JS.
- **Settlement.** Preserve cumulative bucket semantics and serialize heartbeat and final settlement. The Python in-process ledger prevents double debits across concurrent callbacks in the same job. A replacement worker or lost response after a successful debit needs durable idempotency. Verify whether existing RPCs can supply that contract. If they cannot, transact the cumulative ledger and debit together in a narrow DB operation, keyed by call and scoped to the verified user. Test the committed-but-response-lost case, overlapping finalize/heartbeat, insufficient funds, stale jobs, and replay after a process kill.
- **Records and reconciliation.** Write the existing `call_sessions` contract for lifecycle and link it to the conversation. Keep canonical turn IDs in `conversation_messages`. Report a single `usage_events` entry per finalized call, including available evidence when customer credits are zero or total provider cost is unknown. Verify existing consumers of `call_sessions.transcript`, including call analysis and admin reports. Choose a compatible projection or migrate readers before canary. Verify account erasure against any projection, queue, retention or memory write path introduced. [Thread schema](../apps/web/supabase/migrations/20261118130000_create_conversations.sql), [lease and append RPCs](../apps/web/supabase/migrations/20261118170000_create_voice_conversation_leases.sql), [analysis reader](../apps/web/app/api/call-sessions/analyze/route.ts)

### Inworld quality and memory

Use the same consented clone, character, locale, microphone clips and turn scripts on both workers. Compare two things independently. First hold the provider configuration and text constant to isolate SDK and synthesis context differences. Then compare the intended full cascade with the JS direct Grok path. Include the saved clone, English and Spanish, bilingual turns, natural pauses, repeated replies, fast interruptions and text interleaving. Have a listener compare continuity, pronunciation and interruption recovery without seeing which worker produced each recording.

Resolve `synthesisContext.previousRequests` with a public plugin API if available, or a narrowly owned extension and a wire-level contract test. Carry the five-reply and character budget, including multibyte text, reconnect, aborted replies and separation between users. Decide whether to preserve this behavior or accept a measured difference before default routing. Apply the same standard to the pinned xAI STT adapter. [Python context adapter](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/inworld_voice.py), [JS provider compatibility](../apps/voice-agent/README.md#provider-compatibility)

Use the same opt-in and shared/character memory scopes throughout the cutover. Port checked extraction with the same model settings, storage keys and correction semantics. Extract only newly committed eligible turns, exclude seeded history and internal instructions, preserve hard boundaries on corrections, and check consent again before writing. One accepted conversation range gets one writer, even during retries or a rollback. Memory faults degrade to thread context. A read-only memory session is suitable for a disclosed internal test. For a user-facing replacement, prove write parity or approve a reduced feature contract explicitly. [Python memory code](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/memory_extraction.py), [JS shared memory](../packages/voice-chat/src/memory.ts), [JS memory hook](../apps/voice-agent/src/memory.ts)

### Logs, alerts, and privacy

Keep stable correlation across the web route, job, database and provider requests. Every admitted call should be traceable with the runtime, release, room name and SID, job ID, call ID, status, end reason and provider model/request identifiers where available. Use call or room IDs for high-cardinality lookup and low-cardinality labels for alerts. Track pre-admission failures by room and job. Separate speech-to-audio latency from typed-response latency. Emit structured counters for dispatch acceptance, first audio, unexpected disconnects, provider faults, billing discrepancies, stale leases and unreported usage.

Use Axiom and Sentry as the existing operator surfaces. Ship structured production logs from every replica with bounded buffering and shutdown. LiveKit's documented drains include Sentry and syslog but do not list Axiom as a direct destination. Choose one forwarder or a bounded in-process shipper, and exercise both successful delivery and destination outage. Use LiveKit analytics for transport diagnostics. Keep audio and raw text out of log payloads and trace attributes, leave recording off for the pilot, and confirm the host's telemetry retention settings. Validate once using a deliberately failed test call by tracing it from room to provider, billing and final state. [Python Axiom shipper](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/axiom_logging.py), [Python tracing](https://github.com/gianpaj/sexycall/blob/eb0cc63/README.md#agent-tracing-in-sentry), [LiveKit log drains](https://docs.livekit.io/deploy/agents/log-drains/)

### Baseline checks for this assessment

The SexyVoice worker suite passed all 36 tests. In a clean environment with SexyCall's lockfile, 204 selected tests passed across Inworld, provider accounting, metering, credit exhaustion, transcripts, logging, and shutdown. A reused Python environment with LiveKit 1.6.10 failed two Inworld synthesis-context tests, while the locked 1.8.11 environment passed both. Run the provider compatibility tests against the exact release image on SDK upgrades.

## Evidence required to change the default

1. **Deploy an internal copy.** Start with isolated Supabase and approved test credentials. Prove image reproducibility, registration, private readiness, credential boundaries and call correlation. Test the old Python entry point in real browsers with the shared frontend SDK version. Collect cost and latency baselines alongside Python.
2. **Run shadow accounting and parity fixtures.** No customer wallet writes in this phase. Reconcile synthetic wallets and call rows, then run matched calls with real speech and saved clones. Use the existing plan's minimum of 20 paired scripted turns per runtime for initial latency diagnosis. Judge reliability from the staged long calls and canary traffic. Report p50/p95 for end-of-speech to first audio, typed first text, interruptions and reconnects. Investigate a first-audio p95 regression over 300 ms as the plan proposes. Require real 30- and 60-minute sessions, including a rollout, a forced worker loss, and a clean redial. Document any missing usage and quality deviations.
3. **Canary only eligible Inworld calls.** Obtain agreement on target host and cost budget, acceptable voice differences, pilot duration and cohort, and the customer-visible billing and memory contract. Use a server-side toggle for the cohort with an accountable on-call owner. Confirm database rollback compatibility and read paths before accepting debits. Compare the Python cohort by browser/network, voice and locale, and specify traffic volume and review cadence before expansion. Stop and investigate any verified duplicate debit, cross-account access, untraceable charge or unreconciled active call. Pause expansion for broken saved clones, sustained first-audio or disconnect regressions, a memory regression, or costs above the agreed cap.
4. **Rehearse rollback while both runtimes are available.** Disable new JS admissions and send eligible new calls to the Python route with a compatible configuration. In-flight JS calls keep their assigned worker and accounting role until drained or reconciled. Expose any thread continuity limitation on fallback. Keep new records readable and avoid destructive schema rollback. A process crash must leave a bounded recovery path and reusable thread. Confirm handling of outstanding leases, pending chat runs, billing and memory writes before another retry.
5. **Switch Inworld routing only when the evidence supports it.** Require end-to-end financial correctness, no material voice or mobile regression, predictable recovery, and a maintainable package/patch and deployment burden. Keep Python available during a defined rollback window. If parity requires broadly forking Agents JS, operating a second production pipeline without meaningful product benefit, or accepting billing or long-call risk, keep Inworld on Python and revisit the shared product contracts there.

The decision before implementation is whether to fund the isolated deployment and comparison, with LiveKit Cloud as the first host to evaluate. Approval to route paying users should follow the evidence and rollback rehearsal.
