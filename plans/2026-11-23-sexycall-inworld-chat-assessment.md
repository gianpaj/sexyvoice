# Can SexyCall power the Inworld chat and call experience?

**Assessment date** 2026-11-23

**Source baselines** SexyCall `eb0cc63`, SexyVoice `b0dcb1c3`, LiveKit Agents Python `1.8.11`

## Recommendation

**Use the existing SexyCall Python worker for Inworld calls and keep standalone text chat in Next.js.** This is the shorter route to a pilot if the goal is to ship one conversation that can move between typing and speaking. It keeps the Inworld clone behavior, voice billing, memory writes, call limits, logging, and Fly deployment that already serve the Python cascade. The new work is connecting that worker to the product's shared thread and proving the handoff under failure.

1. **Python calls and Next.js text generation.** My pick for the pilot. Keep the current page, TanStack chat transport, and Supabase conversation storage. Reuse LiveKit's text input during calls. Port the JS worker's thread behavior to Python and make both modes use the same admission contract.
2. **Python generation for calls and standalone chat.** Viable if maintaining the same prompt and memory behavior in two languages becomes costly. Keep auth, the browser endpoint, and stream replay in Next.js. Move standalone generation behind an authenticated service or job consumer in SexyCall. That adds a new production execution path with its own timeouts, recovery, and capacity.
3. **Finish the JS call worker.** A better fit if the long-term priority is shared TypeScript generation code and keeping web and Inworld worker changes together. It requires rebuilding or porting more established Python call behavior before paid traffic. [JS migration assessment](2026-11-23-inworld-worker-migration-assessment.md)

“Text chat” covers two paths. During a call, typing replaces the microphone for that turn and the assistant answers aloud. Between calls, the app streams an LLM reply over HTTP with no LiveKit room. Only the first path naturally lives in the existing SexyCall worker.

## The work that determines production readiness

### One admission decision

Next.js and the JS worker share a per-user `voice_conversation_leases` row. Postgres applies the same account lock to that lease and the Python `call_sessions` insert. A linked Python call uses its active billing row for admission and associates each voice turn with that row. Cross-repo tests race a chat claim with a legacy call insert in both directions. [Shared admission migration](../apps/web/supabase/migrations/20261123190000_share_conversation_admission.sql)

The pilot worker must hold the call claim through generation, durable transcript flush, and accounting finalization. A linked call's active row survives the JS lease duration. Exercise cleanup of stale rows after a crash and completion after a startup failure. The status RPC reports an active call to chat until that row completes. [Python call store](https://github.com/gianpaj/sexycall/blob/eb0cc63/src/call_session_store.py)

### One canonical thread and compatible call reporting

Use `conversations` and `conversation_messages` for the user's continuous thread and link `call_sessions.conversation_id` for lifecycle, analysis, and billing. First keep `call_sessions.transcript` as a compatibility projection of the call while analysis and admin still read it. The thread and existing projection may contain the same call text. A single ordered ingest path should feed both and preserve a stable item ID, roles, correction rules, interruption state, and call association. If product analytics needs to distinguish keyboard input from STT, retain that modality separately from the fact that the turn occurred during a call.

Avoid backfilling historic calls for the pilot. They already have their existing transcript. Start new linked threads from current pilot interactions. The deletion action erases threads, clears the user's call transcripts, and deletes their memories. The thread foreign key unlinks the retained call row. Verify that a late Python checkpoint or memory flush cannot restore erased text or memories, including when deletion races an active call. Review retained usage and billing records under the existing policy. [Thread schema](../apps/web/supabase/migrations/20261118130000_create_conversations.sql), [account deletion action](../apps/web/app/actions.ts), [account erasure migration](../apps/web/supabase/migrations/20261123150000_erase_account_conversations.sql), [analysis reader](../apps/web/app/api/call-sessions/analyze/route.ts)

### Keep the two billing paths explicit

- **Active call.** Use SexyCall's existing clock, first-speech rule, 10-second waiver, 500 credits per started 30-second bucket, low-credit warning, and duration limit. Typing in that call is part of the call charge. Keep provider cost for free and failed calls where observable. Exercise a lost response after a debit and overlapping finalization on this path. The in-process ledger covers concurrent callbacks within a job. Prove durable replay safety at the database boundary before extending billable admission or automatic retries. [Python billing and usage](https://github.com/gianpaj/sexycall/blob/eb0cc63/docs/BILLING_AND_USAGE.md)
- **Standalone chat.** The spike records model usage and does not debit the wallet. Implement reservation and settlement once per run in the shared database. Use the rate version specified in the product plan and round once after summing all token charges. Preserve the free 10,000-credit grant and keep customer credits separate from provider spend. Decide what happens when usage is missing or a reply stops halfway, and test the release or reconciliation of reserved credits for expired runs. Moving generation to Python does not remove this work. [Chat pricing and credit safety](2026-11-16-chat-first-conversations-and-calls.md#token-billing-and-credit-safety), [run state schema](../apps/web/supabase/migrations/20261123140000_create_voice_chat_runs.sql)

## Deployment and test ownership

The recommended split uses the current Next.js deploy and the existing Python worker image and Fly operations. Build and exercise the same Python image against an isolated LiveKit dispatch and Supabase project before enabling a cohort. Apply additive DB changes first. Deploy a worker that accepts the new versioned dispatch while serving legacy calls, then enable the matching Next.js route for the test users. Keep the prior route for rollback. Turn off new linked calls first during rollback, then drain or reconcile existing calls and leases. Leave saved threads accessible for text continuation.

The existing Fly setup has a 300-second stop timeout. A 60-minute call can still be interrupted by a worker deployment. If preserving calls through routine releases is a ship criterion, rehearse an explicit drain before stopping the old worker. For unexpected loss, prove bounded claim release, accounting recovery, and redial from committed history. Reuse Axiom, Sentry, and call/provider correlation, and add conversation ID, call or run ID, deployment revision and end reason where applicable. Check that new logs and traces omit message text and provider credentials. Distinguish dispatch, microphone/media, LLM, Inworld, and persistence failures. ## If Python also owns standalone generation

Keep the browser's public auth and SSE path in Next.js. After the DB admits a run, an authenticated internal request or durable job hands Python the run ID. Python claims generation once, loads the authorized thread and bounded context, calls the LLM without creating a LiveKit room, and persists reply snapshots and normalized usage through the existing DB contract. Next.js can continue to stream those snapshots to the browser. Use an authenticated service identity and the admitted run record to derive the owner and conversation. Cover loss of the handoff after admission, duplicate delivery, timeout, worker restart, erase during generation, and a slow Python generator competing for resources with voice calls.

A separate Python process keeps standalone chat capacity and releases independent from the real-time worker. If the pilot can treat a dead generator as an interrupted reply, it can reuse the current bounded replay behavior. If the product requires generation to continue through worker death, budget for durable job ownership and an explicit recovery policy. Chat retry and provider billing must remain idempotent regardless of which process emits the SSE. Keep the wire format in one place, including its offset semantics for Unicode and the existing run-ID mapping. Only move SSE to Python if a measured Next.js delivery problem justifies that additional migration. [Current replay implementation](../apps/web/lib/voice-chat/chat.ts), [TanStack persistence internals](https://tanstack.com/ai/latest/docs/persistence/internals)

Both voice paths need the same database guarantees for admission, thread history, erasure, and credit settlement. Both need real-device and deployed call tests. That is reusable work if the dispatch contract lets either worker own a call while the browser and thread schema stay stable. The JS spike already gives us the interface, thread flow, and browser scenarios to carry forward. [JS assessment](2026-11-23-inworld-worker-migration-assessment.md), [spike verification](../apps/voice-agent/README.md#verification)

Choose the Python split when launching the product soon is the priority. Reconsider JS when shared reply code would materially shorten recurring product changes and an isolated JS deployment has passed clone, billing, memory, and long-call checks. Consider moving standalone generation to Python only when actual prompt or memory drift between the two codebases warrants the added operational path.

## First pilot proof

Start with one real saved-clone thread that survives chat → call → typed and spoken turns → chat → reload while producing one correctly linked call record and the expected accounting. Follow it with the cross-route race and worker-loss tests before accepting customer credits.
